# verification

单元测试证明函数对，验证证明功能能用。产出是两份可重复使用的资产：**功能地图**与**一键驱动脚本**，放仓库里，任何会话都能重跑。

## Leading Words

| 术语 | 定义 |
|------|------|
| **验证资产** | 功能地图 + 驱动脚本；随仓库版本化，不依赖某次会话的临时命令 |
| **功能地图** | 每个用户可见功能 → 触达方式 → 前置数据 → 期望结果 |
| **一键驱动** | 一条命令跑通核心路径，用退出码判断成败 |
| **证据** | 命令 + 输出片段 + 退出码；"看起来没问题"不算证据 |

## 步骤

### 1. 盘点功能入口

读 README、CLI 帮助、路由表、`package.json` 的 scripts、容器编排文件，列出用户实际能触达的功能与入口。

- 入口不明确时用 `grilling` 只问 Decisions（哪些算核心路径），Facts 自己查
- 完成标准：入口清单覆盖所有对外可触发路径

### 2. 写功能地图

写入 `docs/08-Testing/功能地图.md`，每条包含：功能、触达方式、前置数据、期望结果、是否冒烟。

- 冒烟项控制在 10 条以内，其余标"按需"
- 触达方式必须可复制执行（命令、HTTP 请求或 UI 路径）
- 完成标准：每条都能被另一个人照着跑一遍

### 3. 生成一键驱动

在项目约定位置生成脚本（默认 `scripts/verify.*`，跟随项目技术栈），按功能地图顺序执行冒烟项。

- 失败即非零退出，并打印失败的功能名与关键输出
- 支持干净环境执行：固定 fixture、容器或种子数据
- 完成标准：成功退出码 0；任一功能失败时能定位到功能名

### 4. 接入实现循环

给 `implement` 使用：

- 改动前跑一次，确认基线是绿的
- 改动后再跑，输出作为 code-review 的 `已复现` 证据
- 失败 → 按功能名定位：逻辑问题回 `implement` 修复，难复现交 `diagnosing-bugs`
- 完成标准：Task 收尾记录里附命令、退出码与失败项

## 边界

- **与 tdd 分工**：tdd 覆盖逻辑正确性，verification 覆盖"应用能起来、功能能触达、结果符合预期"
- **核心路径优先**：10 条以内、稳定可重跑，比覆盖面更重要
- **跳过要留痕**：外部依赖不可用时打印 skip 原因，退出码不得静默为 0
- **纯库项目**：用最小示例脚本调用公共 API，同样产出证据

## Gotchas

- 功能地图写成测试用例清单 → 验证关心"用户怎么触达"，不是断言细节
- 脚本依赖本地脏数据 → 干净环境跑不通；先固定 fixture 或容器
- 失败时静默跳过 → 退出码仍为 0，验证变成摆设
- 只跑单测就宣称验证通过 → 单测不证明应用能启动
- 功能地图一次写 30 条 → 维护不动就会腐烂；先 10 条核心路径
