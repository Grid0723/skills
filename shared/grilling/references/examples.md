# Grilling 交互示例与边界场景

## 典型交互流程

### 场景 1：模糊需求 → 清晰功能定义

```
用户: 我想给 TDX 加个自动提醒功能
AI:   你期望的提醒触发条件是什么？是价格突破某个阈值，还是成交量异常？
      （选项：A.价格变动 B.成交量异常 C.技术指标信号 D.定时推送）

用户: A，价格突破
AI:   对"突破"的定义：是横盘整理后的突破，还是单日涨跌幅超过 N%？
      此外，需要提醒哪些股票？全部 A 股还是自选股？

用户: 单日涨幅超过 5%，自选股
AI:   明确了。触发条件：自选股单日涨幅 ≥5%，方式：弹窗/声音？（不需要文件——继续 to-prd）

→ Grid 进入 to-prd 阶段
```

### 场景 2：能探索不提问

```
用户: TDX 的 get_financial_data 返回值是什么格式？
AI:   （查阅 tdx-quant-docs skill 中的参考文档）
      → 查阅结果：返回 Dict[str, pd.DataFrame]，键为股票代码，DataFrame 列包含 FN 财务指标。

      请问你是要了解某个具体指标的字段名，还是需要了解返回值处理的完整例子？

用户: 了解字段名即可
AI:   主要字段包括 FN001-FN584，其中 FN001 为每股收益、FN002 为每股净资产...
      （不提问了——用户的问题已被文档回答）
```

### 场景 3：2-3 轮未收敛 → 建议 PRD

```
用户: 我想要一个更好的数据存储方案
AI:   "更好"指的是更快、更省空间、还是更方便查询？（选项）

用户: 都快一点吧
AI:   了解。当前你遇到的具体瓶颈是什么？日 K 线查询慢？分钟线存储大？还是财务数据写入慢？

用户: 都慢
AI:   我们已讨论了两轮，归纳一下：你希望对存储层做综合性能优化，但具体瓶颈和优化目标还不够清晰。
      建议先产出一份 PRD 草案，在写 PRD 的过程中问题会自然收敛。是否同意？

→ Grid 进入 to-prd 阶段，用 PRD 草案驱动余下的讨论
```

## 边界场景

### 用户跳过拷问

```
用户: 我要加 ETF 数据获取器，直接用 tdx-quant-docs 查 API 就行，不需要拷问
AI:   了解。需求清晰——跳过拷问阶段，直接进入 PRD。

→ Grid 跳过拷问，进入 to-prd
```

### 需求涉及多个项目

```
用户: 我想把 TDX 的数据格式统一改成 Parquet
AI:   这个改动会同时影响 TDX 项目（数据写入端）和可能读取这些数据的分析脚本。
      当前有哪些项目或脚本依赖 TDX 数据库的直接读取？（一问）

→ 如果涉及 DevOps 级别的大规模重构 → 标记为 wayfinder 候选
```

### 用户说"不确定，你给建议"

```
用户: 你觉得用 PostgreSQL 还是 ClickHouse？
AI:   这取决于你的查询模式（复杂分析 vs 简单查询）、数据量级和延迟要求。
      但这个问题代码库本身无法回答——让我问三个关键问题：
      1. 主要的查询模式是什么？大批量聚合 OLAP 还是单行点查 OLTP？
      2. 日均数据增量大概多少行？
      3. 对查询延迟的要求是多少毫秒？

→ 逐步缩小选择范围
```

## 核心原则速查

| 原则 | 做法 | 反例 |
|------|------|------|
| 一次一问 | 每次一个问题，带选项引导 | 一次抛出 5 个问题 |
| 能查不答不问了 | 文档/代码有答案→直接查→告知结果 | 明明能查到还问用户 |
| 3 轮不收敛→草案 | ≥3 轮还模糊→建议 PRD 草案驱动 | 无限追问直到用户烦躁 |
| 大决策拆小问题 | 数据库选型→先问查询模式，再问数据量 | "你数据库有什么需求？" |
