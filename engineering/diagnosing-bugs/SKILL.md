# diagnosing-bugs

难 bug 不靠猜。先让问题**必须**复现，再逐步缩小范围。

## Leading Words

| 术语 | 定义 |
|------|------|
| **红色反馈环** | 一个能在该 bug 上稳定失败的测试/脚本；没有它不进入修复 |
| **Mutation diff** | 故意改动代码，确认测试真的会红——防止"改了等于没改"的假红 |
| **最小化** | 把输入、路径、环境缩到仍能复现的最小集合 |
| **埋点** | 日志、断言、指标，用来验证或排除假设，而不是猜 |

## 入口判定

| 场景 | 动作 |
|---|---|
| 稳定可复现的 bug | 直接进入阶段 1 |
| 偶发 bug | 先做阶段 1 的"高频复现"（循环/压力/并发） |
| 性能回归 | 阶段 1 用基准脚本，阶段 5 看分布而非平均值 |
| 已知根因的小修 | 可跳过本 skill，直接 `implement` |

## 步骤

### 1. 建立红色反馈环

- 写一个最小测试/脚本，能在当前代码上**稳定失败**
- 偶发问题：提高触发频率（循环、并发、缩小超时）
- 无法复现 → 先补日志与监控，不进入修复

- 完成标准：失败可重复，输出可判断

### 2. 验证"红"是真的（Mutation diff）

- 故意改一行代码，确认测试从红变绿或行为变化
- 改动后测试**仍然红** → 说明测试没有真正覆盖问题，回到阶段 1

- 完成标准：mutation 能改变测试结果

### 3. 最小化

- 缩小输入数据
- 减少调用路径
- 固定环境（版本、配置、并发数）
- 二分定位：注释/跳过一半逻辑，确认问题是否仍在

- 完成标准：复现集合已最小

### 4. 形成假设

列出 3–5 个候选原因，按概率排序，每个假设写：

```text
假设：<原因>
验证方式：<埋点/实验>
预期：<若成立，应该看到什么>
```

- 完成标准：假设可被证伪

### 5. 埋点验证

- 用日志、断言、指标或断点验证假设
- 一次只验证一个假设；排除后记录原因
- 性能问题：看 p50 / p95 / p99、内存曲线、GC、I/O 等待，不看单一平均值

- 完成标准：根因被证据确认，而非"看起来像"

### 6. 修复与回归

1. 修复根因（不是绕过症状）
2. 红色反馈环转绿
3. 补充回归测试，防止复发
4. 涉及设计取舍 → 写 `docs/05-ADR/ADR-<nnn>-<名>.md`
5. 需要正式提交 → 交 `implement` 或 `git-commit`

- 完成标准：测试绿，回归测试已加，根因已记录

## 输出

```markdown
## 诊断报告

- 现象：
- 复现方式：
- 根因：
- 证据：
- 修复：
- 回归测试：
- 遗留风险：
```

## 边界

- 没有红色反馈环，不进入修复
- 不把"加个 try/catch"当修复
- 不为了通过测试而改测试断言
- 不跳过 mutation diff（假红是最常见的浪费时间来源）

## Gotchas

- 没复现就开始改代码 → 改多处仍不知道哪处生效，先建红色反馈环
- 测试是红的，但改动代码后仍然红 → 测试没覆盖问题，先做 mutation diff
- 只在本地加日志、不改断言 → 下次重构日志被删，问题复发
- 性能只看平均值 → 尾部延迟被掩盖，必须看 p95/p99 与分布
- 修复症状而非根因 → 同一 bug 换个入口再次出现
