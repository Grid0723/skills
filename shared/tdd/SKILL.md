# tdd

测试驱动开发围绕**接缝（seam）**展开——系统可独立测试的边界。本 skill 定义接缝标准和常见反模式。

## Leading Words

| 术语 | 定义 |
|------|------|
| **接缝（Seam）** | 系统可独立测试的边界——所有测试和设计围绕接缝展开 |
| **红→绿→重构** | 先写失败测试 → 最小实现使其通过 → 清理代码 |
| **一次一个** | 每次只处理一个测试，通过后再写下一个 |

## 标准

- 每个新功能从**失败的测试**开始，测试描述预期行为
- 测试应当测试**接缝**——模块或函数的独立可验证边界
- 实现代码量应**最小化**——刚好让测试通过，不写多余逻辑
- 测试通过后**立即重构**——消除重复、改善命名、提取公共逻辑
- 重构后**运行全部测试**——确保没有破坏已有功能

## 反模式

以下行为违反 TDD 纪律：

- 先写实现再补测试——测试沦为验证而非驱动
- 一次写多个测试——丧失红绿循环的短反馈优势
- 测试覆盖实现细节而非行为——测试脆弱，重构即破裂
- 跳过重构步骤——技术债务累积
- 写不验证任何接缝的测试——"为了测试而测试"

## 项目专属测试规范

各项目可能有附加的测试规范（如数据管道项目的集成验证、全栈项目的单元 + lint）。这些通过项目 AGENTS.md 中的 `skills` 声明加载。
