# Grid

软件开发生命周期总编排器。接收任务描述 → 路由判断类型 → 按阶段驱动原子 skill → 编码内循环推进。

## Leading Words

| 术语                             | 定义                                 |
| ------------------------------ | ---------------------------------- |
| **路由（Routing）**                | 判断任务类型（新功能/bug修复/重构/配置变更），跳过不必要的阶段 |
| **管道（Pipeline）**               | Grid 的阶段序列——每一阶段有明确的产出物和退出条件       |
| **技能推荐（Skill Recommendation）** | 扫描项目 AGENTS.md 注册的技能列表，根据任务类型动态推荐  |
| **编码内循环（Inner Loop）**          | 开发计划中的任务逐项推进：写测试→写实现→审查→标记完成       |
| **审批门**                        | PRD、开发计划等正文必须先展示草案，用户确认后写入         |

## 阶段序列

```bash
路由 → 拷问 → PRD → 拆Issue → 编码(内循环) → 超大任务规划
```

## 步骤

### 1. 路由——判断任务类型

读取用户输入，判断类型，决定走哪些阶段：

| 类型 | 判断条件 | 跳过 |
|------|---------|------|
| 新功能 | 用户描述了一个尚不存在的功能 | 无 |
| Bug 修复 | 用户描述了异常行为或错误 | PRD；难 bug 先走 `diagnosing-bugs` 建红色反馈环，再 `implement` |
| 重构 | 用户要求改结构不改功能 | PRD（拷问→拆Issue→编码→审查） |
| 配置变更 | 用户要求改配置/依赖/环境 | PRD、拆Issue（拷问→编码） |
| 轻量改动 | 单文件、≤50 行、不改公共 API/数据模型/依赖，且已有测试覆盖 | PRD、拆Issue（直接 tdd → code-review） |
| 项目立项（已有项目计划） | 项目已通过 Fabric `project-lifecycle` 立项，检测到 `项目计划.md`/`总览.md`（Obsidian 产物） | **无**——必须走完整管道 |

> [!warning] 已有项目计划 ≠ 可跳过阶段
> Fabric 产出的 `项目计划.md` 只是**按功能模块分组的任务清单**（无 seam/范围/风险标注），不是 PRD，也不是开发计划。**严禁**将其判定为"现成 PRD+开发计划"而跳过拷问/PRD/拆 Issue。项目计划仅作为拷问阶段的输入素材。

> 轻量改动跳过后必须说明「为什么算轻量」；任一条件不满足 → 走完整管道。

**技能推荐**：扫描当前项目 AGENTS.md 中的 `skills:` 声明列表，根据任务类型推荐相关技能。

> 示例输出：
> 本次任务：新增 ETF 数据获取器（新功能）
> 阶段序列：拷问 → PRD → 拆 Issue → 编码 → 审查
> 建议加载：项目专属 skill（按 `AGENTS.md` 的 `skills:` 声明）+ `tdd` + `code-review`
> 是否确认？

- 完成标准：任务类型已判定，阶段序列已确认，技能推荐已展示

### 2. 拷问——引用 grilling

加载 `grilling` skill，执行一问一答式拷问。把模糊想法具体化到可写 PRD。

- **已有项目计划时仍须完整拷问**：即使项目已通过 Fabric 立项（存在 `项目计划.md`/`总览.md`），拷问阶段也不可跳过——以项目计划为素材验证需求完整性，拷问边界条件与模糊点，全程询问用户确认
- 拷问收尾必须输出共识摘要，用户确认后才进入 PRD
- 完成标准：用户确认共识摘要，或明确表示"开始写 PRD"
- 如果用户需求本已足够清晰 → 说明判定依据（哪些决策已明确）后跳过，直接进入 PRD

### 3. PRD——引用 to-prd

加载 `to-prd` skill，综合对话生成 PRD 草案。接缝优先——每个 seam 对应可独立验证点。

- 完成标准：PRD 已写入 `docs/01-Requirements/PRD-xxx.md`

### 4. 拆 Issue——引用 to-issues

加载 `to-issues` skill，PRD → tracer bullet 垂直切片，写入 `docs/07-MVP/开发计划.md`。每个 Task 可独立演示和验证；编号格式 `<项目码>-S<阶段>-F<功能>-T<任务>`（一个 Task = 一个 commit）。

拆解完成后自动提示调用 `git-branch`：
> 建议创建分支 `feature/<项目码>-S<n>-F<n>`，是否执行？

- 完成标准：开发计划已写入，分支已创建（如适用）

### 5. 编码——引用 implement

加载 `implement` skill，按 Task 执行：

- 单任务（默认）：`implement <Task ID>` → 读原文 → 确认 seam → tdd → code-review → 一个 Task 一个 commit
- 批量：`implement S<n>` → 建依赖图 → 按 ready frontier 执行 → 失败即停

- 完成标准：开发计划中对应 Task 标记 `[x]`，每个 Task 一个 commit

### 6. 超大任务规划——引用 wayfinder（条件触发）

仅当任务是 DevOps 类大型重构/迁移（如"pandas 迁移到 Polars"）时触发。加载 `wayfinder` skill。

- 完成标准：共享地图已建立，第一个 ticket 已规划

## 全局约束

编码阶段全程遵守：
- `git-guardrails` —— 禁止自动 git add/commit/push
- `git-commit` —— 完成一个小功能点立即提交

## 内部引用

| 阶段 | 引用的原子 skill |
|------|-----------------|
| 拷问 | `grilling` |
| PRD | `to-prd` |
| 拆 Issue | `to-issues` → `git-branch` |
| 编码 | `tdd` → `code-review` → `git-commit` |
| 超大任务规划 | `wayfinder` → `git-branch` |

## 项目技能扫描

编码阶段扫描项目仓库 AGENTS.md 中的 `skills:` 声明，动态加载对应技能。技能列表随项目不同而热插拔。

## Gotchas

- 把 Fabric 的 `项目计划.md` 当成现成 PRD → 它只是拷问素材，仍须完整 PRD 与拆 Issue
- 已有项目计划时跳过拷问 → 拷问不可跳过，计划只用于验证需求完整性
- 编码前未确认 seam → 先与用户对齐测试接缝，再写测试
- 未展示阶段序列就直接编码 → 先展示「类型 + 阶段序列 + 技能推荐」并等待确认
