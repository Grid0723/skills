# Grilling 交互示例与边界场景

## 典型交互流程

### 场景 1：模糊需求 → 一次一问

```
用户: 我想给 TDX 加个自动提醒功能
AI:   第一个决策：提醒在什么条件下触发？
      （A. 价格突破阈值  B. 成交量异常  C. 技术指标信号  D. 定时推送）

用户: A，价格突破
AI:   （先查代码确认当前自选股与行情接口，属于 Facts，不问用户）
      第二个决策：价格突破的判定口径是什么？
      （A. 横盘整理后的突破  B. 单日涨跌幅超过 N%）

用户: B，单日涨幅超过 5%
AI:   第三个决策：提醒范围是全部 A 股还是自选股？

用户: 自选股
AI:   已确认三项。其余信息（行情接口、自选股存储）已从项目文档查明。
      → 进入共识确认（见场景 4）
```

### 场景 2：Facts 自查，不抛回用户

```
用户: TDX 的 get_financial_data 返回值是什么格式？
AI:   （查阅项目 API 文档与源码）
      返回 Dict[str, pd.DataFrame]，键为股票代码，列为 FN001-FN584 财务指标。
      （问题已被 Facts 回答，不再反问用户）
```

### 场景 3：3 轮不收敛 → 草案驱动

```
用户: 我想要一个更好的数据存储方案
AI:   第一个决策："更好"优先看哪一项？（A. 查询速度  B. 存储空间  C. 维护成本）

用户: 都快一点吧
AI:   第二个决策：目前最明显的瓶颈在哪？（A. 日 K 线查询  B. 分钟线存储  C. 财务数据写入）

用户: 都慢
AI:   第三个决策：优化目标更接近哪一种？（A. 单次查询 <1s  B. 全量回测 <10min  C. 存储减半）

用户: 说不清
AI:   已连续 3 轮未收敛。建议先写一份 PRD 草案，把瓶颈假设列出来，用草案驱动剩余讨论。
      是否同意？
```

### 场景 4：共识确认门控

```
用户: 差不多可以了，开始吧
AI:   先对齐共识（3-5 行）：
      - 触发：自选股单日涨幅 ≥5%
      - 通道：弹窗 + 声音
      - 范围：自选股，不含持仓
      - 未定：盘中实时还是收盘后计算
      以上理解是否一致？确认后我才进入 PRD。
```

### 场景 5：用户要求跳过拷问

```
用户: 别问了，需求很清楚，直接写
AI:   可以。跳过拷问的风险点有两个：
      1. 「突破」的判定口径未定，可能返工测试；
      2. 提醒范围未定，可能漏掉持仓股。
      我会把这两项作为开放问题写进 PRD；如果后面发现影响实现，再回来确认。
      → 记录跳过项，进入 to-prd
```

## 边界场景

### 需求涉及多个项目

```
用户: 我想把 TDX 的数据格式统一改成 Parquet
AI:   （先查依赖：读取 TDX 数据库的脚本与项目）
      这个改动会影响 3 个读取方：分析脚本 2 个、交易助手 1 个。
      第一个决策：这次一起迁移，还是先只改写入端？
```

### 用户说"不确定，你给建议"

```
用户: 你觉得用 PostgreSQL 还是 ClickHouse？
AI:   这取决于查询模式。第一个决策：主要负载是哪一种？
      （A. 大批量聚合分析  B. 单行点查  C. 两者都有）
      → 按回答逐轮收敛，一次只问一个
```

## 核心原则速查

| 原则 | 做法 | 反例 |
|------|------|------|
| 一次一问 | 每轮一个问题，带选项引导 | 一次抛出 5 个问题 |
| Facts 自查 | 文档/代码有答案 → 自己查 → 告知结果 | 明明能查到还问用户 |
| Decisions 用户拍板 | 给选项与推荐项，由用户选定 | 替用户决定架构或范围 |
| 3 轮不收敛 → 草案 | 建议 PRD 草案驱动剩余讨论 | 无限追问直到用户烦躁 |
| 确认门控 | 输出共识摘要，等明确确认再进入下一阶段 | 用户说"差不多"就直接写代码 |
