# 项目计划模板示例

## 完整的项目计划

```markdown
## 项目计划: <项目名>

### 模块 A——核心数据
- [ ] Task A1: <描述> — 验证: <如何确认> #项目/<项目名>
- [ ] Task A2: <描述> — 验证: <如何确认> #项目/<项目名>

### 模块 B——业务逻辑
- [ ] Task B1: <描述> — 验证: <如何确认> #项目/<项目名>
- [ ] Task B2: <描述> — 验证: <如何确认> #项目/<项目名>

### 模块 C——用户界面
- [ ] Task C1: <描述> — 验证: <如何确认> #项目/<项目名>
```

## 任务粒度判断

| 太粗 | 太细 | 合适 |
|------|------|------|
| "实现整个数据获取模块" | "创建 stock_basic 表的 id 字段" | "实现 stock_basic 的 Prisma model + migrate" |
| 无法在一个 session 完成 | 5 分钟完成，但无独立验证价值 | 1-2 个 session 可完成 + 可独立验证 |

**判断标准**：删除这个 Task 后，项目的某个可演示功能是否消失了？如果是 → 粒度合适。如果项目还能正常演示 → 太粗（里面有多个可演示功能）。

## 模块分组原则

| 原则 | 说明 |
|------|------|
| 一个模块 = 一个可独立理解的子系统 | 不用看其他模块就能理解本模块的职责 |
| 3-5 个任务/模块 | 太少不值得分组，太多需要拆子模块 |
| 模块间无硬性依赖最佳 | 有依赖要标注——"B 依赖 A 完成" |
